# Перечитывание сертификата Certbot без перезапуска Grafana

[compose.letsencrypt.yaml](compose.letsencrypt.yaml) — отдельный HTTPS-overlay для уже выпущенного публично доверенного сертификата Certbot. Он применяется после [compose.yaml](compose.yaml), **вместо** `compose.https.yaml`. Режим с произвольными файлами сертификата, ключа и CA остаётся в `compose.https.yaml`; существующий E2E использует именно его.

Grafana читает `live/<имя>/fullchain.pem` и `privkey.pem` и проверяет изменения раз в минуту. Подключены только два каталога одной lineage (имени сертификата Certbot): `live/<имя>` и `archive/<имя>`, оба только для чтения. Их относительное расположение сохраняет ссылки `../../archive/<имя>/…`. ACME account, renewal-конфигурация и чужие сертификаты не монтируются. Не подставляйте общий каталог secrets: он может содержать ключ App, CA и пароли БД.

## Подготовка на Linux

Нужны обычный Docker Engine без переназначения UID, существующий Certbot и уже настроенное продление. Rootless Docker, user namespace remapping и права Windows этим рецептом не покрываются. Overlay не выпускает сертификат, не устанавливает Certbot и не меняет расписание или hooks.

В игнорируемом `.local/analytics.env` задайте параметры своей установки:

```dotenv
GRAFANA_DOMAIN=grafana.example.com
GRAFANA_PORT=3301
GRAFANA_TLS_CONFIG_DIR=/etc/letsencrypt
GRAFANA_TLS_LINEAGE=grafana.example.com
GRAFANA_TLS_GID=472
```

`GRAFANA_TLS_CONFIG_DIR` — абсолютный путь на хосте Docker, в том числе при контейнерном Certbot. `GRAFANA_TLS_LINEAGE` — одно имя каталога без `/` и `\`, не равное `.` или `..`; оно может отличаться от DNS-имени. Проверьте, что оба каталога существуют, а ссылки ведут только в соответствующий `archive/<имя>`. Отсутствующие каталоги Compose не создаёт (`create_host_path: false`).

Закреплённый образ Grafana работает с UID 472. `GRAFANA_TLS_GID` добавляет процессу дополнительную группу для чтения TLS-ключа; 472 в примере нужно сверить с владельцами и доступом на конкретном хосте. Не используйте root-группу или группу посторонних пользователей. Для текущей цели ссылки `privkey.pem` оставьте владельца root, назначьте эту группу и режим `0640`. Сертификат должен быть доступен для чтения, а два подключаемых каталога — для прохода процессу Grafana. Не меняйте права рекурсивно: общие родительские `live` и `archive` на хосте могут оставаться `root:root 0700`, поскольку в контейнер подключаются только вложенные каталоги. До запуска проверьте также ACL и доступ других сервисов к этой же паре.

[Certbot сохраняет группу и групповые права ключа при продлении](https://eff-certbot.readthedocs.io/en/stable/using.html#where-are-my-certificates) начиная с версии 0.29.0. Проверьте установленную версию и поведение hooks, которые могли бы заменить эти права. Команда `local-analytics.mjs permissions` готовит файловые secrets базового стека, но **не настраивает** права Certbot и будущих ключей.

После подготовки базовых secrets по [README](README.md) проверьте конфигурацию и запустите стек:

```sh
docker compose --env-file .local/analytics.env -f analytics/compose.yaml -f analytics/compose.letsencrypt.yaml config --quiet
docker compose --env-file .local/analytics.env -f analytics/compose.yaml -f analytics/compose.letsencrypt.yaml up -d --wait --wait-timeout 180
```

Порты остаются привязанными к `127.0.0.1`, как в базовом Compose. Healthcheck проверяет DNS-имя и цепочку через системное хранилище CA контейнера; сертификат ACME staging ему не подходит. `local:up`, `local:infra` и `local:once` запускают только базовый `compose.yaml`: для HTTPS используйте явно выбранные Compose-файлы во всех последующих командах. Публичный bind, DNS, firewall и способ ACME challenge настраиваются отдельно.

## Существующий сервер с отдельным Compose

Этот репозиторий не управляет независимыми серверными `compose.json` и их генераторами. Изменение overlay само по себе их не обновляет. Для воспроизводимого восстановления перенесите в источник генерации серверного Compose настройки `environment`, два `volumes` и `group_add` из overlay, сохранив действующие порты, URL, healthcheck, лимиты, secrets, данные и остальные сервисы. Если TLS уже настроен таким способом, повторное пересоздание контейнера не требуется.

Для установки, которая ещё использует копирование TLS-файлов:

1. Сохраните закрытую копию текущего Compose, настроек доставки, расписания и метаданных прав. Установите фактический источник Compose и параметры запуска; не заменяйте весь серверный файл локальным шаблоном.
2. Подготовьте доступ только к своей lineage. Удалите из сервиса Grafana заменённые файловые TLS-secrets или bind mounts; остальные secrets сохраните. Сохраните Certbot, его cron/timer, challenge, нужные другим сервисам hooks, backup и проверки срока/отпечатка сертификата.
3. Проверьте итоговый Compose. С теми же project name, env и списком файлов один раз выполните `up -d --no-deps --force-recreate --wait grafana`: это кратко прервёт только Grafana. Не используйте `down` для всего стека.
4. Проверьте `healthy`, read-only mounts только своей lineage, чтение пары процессом Grafana и отсутствие доступа к записи. Сравните SHA-256 отпечатки **публичного** leaf-сертификата в источнике, внутри контейнера и в новом HTTPS-соединении с проверкой имени и доверия. Не выводите приватный ключ. Сверьте состояние и время запуска остальных контейнеров с исходным срезом.
5. Отключите только заменённую доставку (копирование и пересоздание Grafana), сохранив её для отката. Если один скрипт совмещает продление, доставку и проверку, уберите из него только доставку. В проверке served/source дождитесь интервала watcher с запасом; сам `healthy` не доказывает, что сервер уже отдаёт новый сертификат.

При откате восстановите прежний Compose и доставку, проверьте актуальность и совпадение старой пары, затем пересоздайте только Grafana. Не откатывайте базу или volumes. После изменения сертификата прежние копии могли устареть: сначала синхронизируйте их прежним проверенным способом.

## Проверка последующего обновления

[Встроенный watcher Grafana](https://grafana.com/docs/grafana/latest/setup-grafana/configure-grafana/#certs_watch_interval) перечитывает пару без перезапуска. В [реализации 13.2.4](https://github.com/grafana/grafana/blob/v13.2.4/pkg/api/http_server.go) он следует ссылкам и обнаруживает изменение по mtime. При временно несовпадающей или недоступной паре сохраняет предыдущую и повторяет чтение через следующий интервал. Поэтому нужны каталоги, сохраняющие видимость новых файлов и ссылок; включения watcher поверх одиночного файлового bind mount недостаточно для надёжной атомарной замены файла.

Проверяйте новое HTTPS-соединение после реального изменения пары и mtime: источник, сертификат из контейнера и served-сертификат должны совпасть, а ID и StartedAt контейнера — остаться прежними. Такую замену можно проверить в изолированном локальном окружении с временным CA и двумя синтетическими парами. `certbot renew --dry-run` сам по себе не доказывает подхват новой пары рабочей Grafana; лишний production-выпуск для этой проверки не нужен.

Существующий E2E проверяет прежний файловый HTTPS-режим, авторизацию и данные. Он не проверяет этот Certbot-overlay, права конкретного VPS или его планировщик продления. После перехода наблюдайте первое штатное продление и сохраните проверку совпадения served/source отдельно от watcher.
