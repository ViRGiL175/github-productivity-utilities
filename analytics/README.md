# Локальная аналитика одного GitHub Project V2

Адаптер читает одну организационную доску через существующий GitHub App и сохраняет наблюдения в PostgreSQL. Grafana использует штатный PostgreSQL datasource с отдельной ролью только для чтения. PostgreSQL хранит аналитические данные; собственная база Grafana остаётся SQLite в отдельном Docker volume.

Node.js и npm должны быть уже установлены. Зависимости адаптера находятся только в `node_modules` этого checkout. PostgreSQL и Grafana запускаются в Docker Desktop; глобальные пакеты, службы, Dockerfile и Buildpacks не нужны.

На Linux файловые Docker secrets сохраняют владельца и права файла хоста. Скрипт запуска использует имеющийся `setfacl`: чтение получает только нужный UID закреплённого образа (PostgreSQL — 70, Grafana — 472); PEM-ключ GitHub App в этот список не входит. Нужны POSIX ACL и обычный Docker Engine без user namespace remapping. Если `setfacl` или ACL недоступны, команда остановится до запуска контейнеров и ничего не установит. Rootless Docker и переназначение UID этой конфигурацией не проверялись.

## Первый запуск

```powershell
npm ci
npm run local:infra
```

Команда создаёт игнорируемые Git каталог `.local`, конфигурацию `.local/analytics.env` и случайные локальные пароли БД/Grafana. Контейнеры имеют отдельное имя Compose project, сеть и volumes. Порты опубликованы только на `127.0.0.1`: Grafana — `3301`, PostgreSQL — `55432`. Anonymous access, public dashboards, snapshots и регистрация отключены.

Заполните `.local/analytics.env` по [примеру](analytics.env.example): точные организацию, номер доски, App ID и список репозиториев этой доски. Не включайте реальные названия, ID, URL проектов или секреты в отслеживаемые файлы. Не используйте эту БД для второй доски: адаптер проверяет закреплённую идентичность источника и отклоняет замену.

После отдельного согласования доступа сохраните существующий PEM-ключ App в `.local/secrets/github-app.pem` и выставьте `ALLOW_GITHUB_APP_KEY_READ=true`. Ключ не передаётся в контейнеры, Grafana, PostgreSQL или GitHub: адаптер читает его для локальной подписи JWT. Не присылайте ключ или мастер-пароль хранилища в чат. Ограничьте доступ к `.local` учётной записью пользователя: POSIX-режимы создаются автоматически; в Windows права наследуются от родительской папки и требуют отдельной проверки ACL.

У App уже должны быть разрешения `Organization Projects: read`, `Issues: read`, `Pull requests: read`, `Metadata: read` и установка в выбранной организации. Адаптер не меняет права App, не создаёт новый ключ и не использует PAT или `gh` credentials. При выпуске временного installation token запрашиваются только перечисленные read-only права и указанные репозитории. Разрешение Organization Projects относится к организации, а не к отдельной доске; выбор единственного проекта дополнительно ограничен кодом и привязкой БД. Сам PEM-ключ обладает полномочиями App, поэтому обращение к нему требует осознанного разрешения.

```powershell
npm run local:up
```

Это одна команда для запуска контейнеров, сборки адаптера и его работы в текущем терминале. Она выполняет первую полную загрузку, а затем сверку через час после последнего успешного импорта. Интервал задаётся `SYNC_INTERVAL_SECONDS=3600` в `.local/analytics.env`; если настройка отсутствует, используется час. Срок следующей сверки проверяется раз в минуту. После перезапуска просроченная сверка запускается сразу; при ошибке GitHub повтор планируется через час, при недоступности PostgreSQL — через минуту. Ошибки подключения, подготовки схемы и простаивающих соединений не останавливают постоянный сбор; режимы одной сверки и миграции завершаются с ненулевым кодом. Терминал должен оставаться открытым. Это не установленная системная служба.

Полезные команды:

| Команда | Действие |
| --- | --- |
| `npm run local:once` | Контейнеры, сборка и одна принудительная сверка |
| `npm run local:status` | Состояние контейнеров |
| `npm run local:down` | Остановка только этих контейнеров с сохранением данных |
| `npm run analytics:build` | Только компиляция адаптера |

Перед `local:down` остановите адаптер сочетанием Ctrl+C в его терминале.

## Проверка данных в Grafana

Откройте <http://localhost:3301>, пользователь `localadmin`. Пароль хранится локально в `.local/secrets/grafana-admin`; не публикуйте его. В Explore выберите datasource **Project analytics** и формат Table.

```sql
SELECT item_id, title, repository, item_type, state, archived
FROM analytics.items
WHERE present
ORDER BY title
LIMIT 50;
```

Проверить объём полной выборки и наблюдения можно запросом:

```sql
SELECT observed_at, item_count, changed_count, missing_count
FROM analytics.sync_runs
WHERE status = 'complete'
ORDER BY completed_at DESC
LIMIT 10;
```

`analytics.item_fields` содержит custom fields и исходные JSON-значения; `analytics.item_iterations` — ID, название, дату начала и длительность Iteration. Архивные карточки сохраняются с признаком `archived`. Исчезнувшие — с `present = false`. Для текущих Iteration соединяйте представление с `analytics.items` и фильтруйте `present`.

## Полнота и история

Готовый [dashboard.json](dashboard.json) содержит четыре панели: типы карточек, распределение Issues по Status, состав текущего Sprint и состояние синхронизации. Его можно импортировать в локальную Grafana; datasource UID — `project-analytics`. Шаблон не содержит названий или идентификаторов частных проектов.

Тип Issue берётся из нативного `Issue.issueType`, а PR и drafts показываются отдельно. Issue без типа не считается историей или эпиком. Авторитетный статус — поле доски `Status`, не `OPEN/CLOSED`. Текущий Sprint определяется полем `Sprint` и интервалом `startDate ≤ дата UTC < startDate + duration`; при отсутствии активного интервала таблица объясняет причину пустого состава.

Коллектор использует GraphQL пагинацию карточек, определений полей, значений полей и вложенных списков. Ограничения в 200 результатов нет. `totalCount`, уникальность ID, курсоры, доступность содержимого и изменение метаданных проекта проверяются до записи. Ошибка API, недоступная карточка или неполная выборка отклоняют наблюдение. GitHub не предоставляет транзакционный снимок всей доски: проверки ловят обнаруженные изменения во время обхода, но не гарантируют единого момента чтения всех страниц.

Первая успешная сверка сохраняет всё. Последующие обновляют текущее состояние и добавляют историческую запись только при изменении содержимого, исчезновении или возвращении карточки. Отметка исчезновения и изменения сохраняются одной транзакцией только после полной выборки. История не удаляется. PostgreSQL advisory lock не допускает одновременного импорта двумя процессами.

`observed_at` — момент завершения наблюдения, а не точное время события в GitHub. Периодический опрос не восстановит промежуточные переходы между двумя наблюдениями. Поле текущей строки `observed_at` меняется только при изменении; свежесть последней успешной сверки смотрите в `sync_runs`.

Grafana получает только SELECT на аналитическую схему; прав записи у datasource нет. Dashboard permissions Grafana OSS не изолируют произвольные запросы datasource. Для другой аудитории создавайте отдельную систему с отдельными credentials и данными.

## Проверки

```powershell
npm run check
npm run analytics:build
```

`check` запускает проверку типов и существующие unit-тесты. Workflow **Test project analytics** выполняет один E2E в существующем GitHub sandbox: настоящая issue с Status и Iteration, полный импорт, повтор без дублей, изменение с историей, исчезновение после полной сверки и запрос через PostgreSQL datasource Grafana. PostgreSQL и Grafana запускаются из этой же Compose-конфигурации с пустыми временными volumes. Тест останавливает временную PostgreSQL до зарегистрированного отказа подключения, запускает её снова и ждёт новый полный импорт тем же непрерывным процессом сборщика. Проверяются потеря простаивающего соединения, повтор подключения и сохранность истории без дублей; запрос через Grafana выполняется после восстановления. Этот перезапуск разрешён скриптом только внутри именованного CI-окружения.

CI использует только GitHub Secrets `ORG_AUTOMATION_APP_ID` и `ORG_AUTOMATION_APP_PRIVATE_KEY`. Помощник получает отдельный токен с записью в тестовые issue и Projects; адаптер сам получает токен только для чтения и проверяет выданные GitHub права и список репозиториев. После прогона cleanup удаляет только элементы этого запуска и закрывает его issue; временные credentials и volumes удаляются. Fork и Dependabot PR не получают секреты. Для ручного запуска выбирайте доверенную ветку. Существующие тесты могут одновременно менять sandbox: адаптер отклоняет меняющийся снимок, E2E ограниченно повторяет только такой сбор, не меняя чужие объекты.

## HTTPS без reverse proxy

Дополнительный `compose.https.yaml` включает HTTPS самой Grafana. Передайте пути к сертификату сервера, его ключу и доверенному CA bundle через `GRAFANA_TLS_CERT_FILE`, `GRAFANA_TLS_KEY_FILE` и `GRAFANA_TLS_CA_FILE`; задайте `GRAFANA_DOMAIN`, соответствующий SAN сертификата. После подготовки TLS-файлов выполните `node scripts/local-analytics.mjs permissions` с теми же переменными окружения: на Linux команда даст Grafana доступ только на чтение. При запуске Compose добавьте этот файл после `compose.yaml`. Healthcheck проверяет цепочку и имя сервера через `curl --cacert`; HTTPS также включает Secure cookies. Автоматического выпуска и продления сертификатов эта конфигурация не делает.

В существующем E2E OpenSSL создаёт временный CA и сертификат с SAN `localhost` и `127.0.0.1`. CA получает только тестовый HTTPS-клиент и healthcheck; системное и браузерное хранилища доверия не меняются. Клиент без этого CA должен отвергнуть соединение. После теста файлы сертификатов, ключи и volumes удаляются.

Этот же E2E проверяет реальную авторизацию: anonymous и signup выключены; без входа нельзя получить дашборд или выполнить datasource query; Viewer читает данные, но не может изменить или удалить дашборд; Admin организации может создать и изменить его. Пользователи создаются только во временной Grafana теста и удаляются после проверки. Это проверка локальных ролей Grafana, без OAuth и проверки членства в GitHub-организации.


## История между сверками

Снимки теперь включают `content.stateReason` и `content.parent` для Issues.
`analytics.items` дополнен `state_reason`, `parent_issue_id` и `content_id`.
Старые записи не переписываются: отсутствие этих полей в них означает, что
данные тогда не собирались. Первый новый импорт создаст дополненные версии.

Необязательный HTTP-приёмник сохраняет события в `analytics.project_events`
в той же PostgreSQL. Поддерживаются:

- `projects_v2_item`: добавление, удаление, архивирование, восстановление,
  конвертация и изменения полей `number`, `single_select`, `iteration`.
  Это включает числовую оценку, Horizon и Status. Текстовые поля, текст
  draft issue, перестановки элементов и комментарии не сохраняются.
- `issues`: открытие, закрытие, переоткрытие, редактирование, удаление и перенос;
  сохраняются только ID, состояние, причина и даты. Редактирование сохраняет
  маленькое наблюдение состояния, поскольку GitHub не гарантирует diff причины.
- `sub_issues`: добавление и удаление родителя/ребёнка; сохраняются ID связи.

События проекта ограничены точным node ID доски, закреплённым первым полным
импортом. События Issues и связей ограничены организацией и
`GITHUB_REPOSITORIES`; они сохраняются и до первого наблюдения Issue на доске,
чтобы порядок доставки не терял новое закрытие или связь. Их наличие само по
себе не доказывает участие Issue в проекте: используйте интервалы участия из
событий проекта и снимков по `content_id`. Две стороны одного изменения
sub-issue могут иметь разные delivery ID; это два свидетельства одной связи,
а не две добавленные истории.

`delivery_id` уникален: повторная доставка подтверждается без второй записи.
Подтверждение HTTP 204 отправляется после завершения INSERT. Ошибка БД даёт
503; неподходящая подпись — 401, повреждённое значимое событие — 422.
Несоответствующие источнику/поддерживаемым действиям события и `ping` получают
204 без записи. Неполная схема события не подменяется догадкой.
Подпись SHA-256 проверяет официальный [Octokit](https://github.com/octokit/webhooks.js),
пакет `@octokit/webhooks` 14.2.0 (MIT, Node.js ≥20).

В журнал не копируются полные webhook payload, тексты историй, комментарии,
пользователи и токены. `data.field` сохраняет `from`/`to`, включая явные `null`
и `0`; отсутствующее значение остаётся отсутствующим. Журнал не изменяет
`item_current` и `item_history`, поэтому задержанная доставка не откатывает
полный снимок. Для HTTP используется отдельный небольшой пул БД, чтобы
длительная пагинация GitHub не блокировала приём событий.

### Включение после согласования развёртывания

1. Выполните обычный полный импорт. Он добавит таблицу и расширит представление
   без удаления существующей истории.
2. Создайте отдельный случайный webhook secret длиной не менее 32 символов в
   защищённом файле. Укажите `GITHUB_WEBHOOK_SECRET_FILE` и, при необходимости,
   `GITHUB_WEBHOOK_PORT` (по умолчанию 8787). Секреты и реальные ID не коммитьте.
3. Постоянный процесс сборщика слушает только `127.0.0.1` по пути
   `/api/github/webhooks`. Режимы `--once` и `--migrate-only` порт не открывают.
   Предоставьте HTTPS через согласованный ingress с проверяемым сертификатом;
   при контейнерном запуске ingress должен достигать loopback контейнера.
   Приёмник не публикует порт и не устанавливает proxy или TLS автоматически.
4. Настройте штатный webhook организации с событиями `projects_v2_item`,
   `issues`, `sub_issues`, `application/json`, тем же секретом и включённой
   проверкой SSL. Для нескольких изолированных сборщиков удобен отдельный
   webhook каждой организации. У GitHub App один общий webhook URL: не
   направляйте его на один из нескольких независимых проектов без маршрутизации.
   App может использовать этот же приёмник, но подписки и маршрут настраиваются
   отдельно. Для событий достаточно `Projects: read` и `Issues: read`;
   права существующего read-only installation token сборщика не меняются.
5. Проверьте delivery в GitHub и строку в PostgreSQL после реального изменения
   поля. До первого успешного импорта события получают 503 и требуют redelivery.

Приёмник ограничивает тело 2 МиБ и время запроса; большие payload отклоняются,
а не сохраняются частично. Если это встречается в доставках, пересмотрите лимит
до повторной отправки. Настройте оповещение по `webhook_failed`,
`webhook_database_connection_failed`, отсутствию успешных сверок и failed
deliveries в GitHub. Входящее отсутствие событий не доказывает исправность
доставки: проект мог просто не изменяться.

GitHub [не повторяет неудачную доставку автоматически](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks).
В Recent deliveries доступны повторы за последние три дня; после сбоя проверьте
и повторите неудачные доставки. Управление webhook и автоматическое восстановление
его доставок не добавлены в read-only сборщик и не расширяют его права.
Ежечасная полная сверка продолжает восстанавливать актуальное состояние, но
не доказывает отсутствие пропущенных кратковременных переходов.

### Время и использование журнала

`received_at` — время приёма, `stored_at` — записи в БД,
`source_updated_at` — переданный GitHub `updated_at` объекта. Последнее не
является гарантированным временем удаления или изменения связи; у `sub_issues`
оно оставлено NULL. Не подменяйте эти даты друг другом. Порядок `revision`
описывает порядок записи, а не причинный порядок событий GitHub.

```sql
SELECT event_name, action, count(*), max(received_at) AS last_received
FROM analytics.project_events
GROUP BY event_name, action;

SELECT delivery_id, event_name, action, source_updated_at, received_at, data
FROM analytics.project_events
WHERE content_id = 'ISSUE_NODE_ID'
ORDER BY received_at, revision;
```

Это дополнительные исходные данные для недельного графика. Нельзя складывать
переходы из снимков и webhook как независимые изменения: они могут описывать
одно событие. Историю до включения приёмника он не восстанавливает. Старый
период и интервалы с неустранёнными failed deliveries остаются приблизительными.
Dashboard, расписание, доступы, размещение и бэкапы эта доработка не меняет.


Приёмник покрыт четырьмя unit-тестами: подделанная подпись и предел тела
(включая chunked), фильтр источника, `null`/`0`/отсутствующее значение,
закрытие/переоткрытие и родительские связи. Штатный E2E дополнен двумя
сценариями с подписанными HTTP-запросами и настоящей PostgreSQL: повторные,
одновременные и запоздалые доставки без изменения снимка; HTTP 503 во время
остановки БД и успешная повторная доставка после восстановления. Webhook
payload в этих сценариях формируется тестом по схеме GitHub: подписка и
доставка от самого GitHub требуют отдельной проверки после развёртывания.
