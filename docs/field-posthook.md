# Поля после добавления PR

`link-pr-to-project.yml` и `safe-dependabot-pr-link.yml` принимают необязательный input `field_posthook` с YAML. Постхук выполняется после добавления PR и повторно при обработке уже добавленного PR: неудавшееся назначение можно повторить без удаления item. Пустой input сохраняет прежнее поведение.

Пример для обоих reusable workflow:

```yaml
with:
  # Остальные inputs выбранного workflow остаются прежними.
  field_posthook: |
    project:
      Horizon: Inbox
    force: false
```

Имена поля и варианта должны точно совпадать с настройками целевого проекта. Default в интерфейсе GitHub не заменяет явное назначение при API-добавлении. Подключение этой настройки у потребителя выполняется отдельно; PR в репозитории автоматизаций не включает её автоматически.

Контроллер `FieldController.apply(config, target)` также доступен для обычных issue:

```yaml
project:
  Priority: P1
  Sprint: Sprint 42
issue:
  Effort: 3
force: false
```

`project` и `issue` — отдельные словари «имя поля: значение». `force: false` — по умолчанию: заполненные поля сохраняются. При `force: true` заменяются только указанные поля. Равные значения в обоих режимах пропускаются. Числа, включая ноль, считаются заполненными. Конфигурация не поддерживает очистку: значения должны быть непустыми строками или конечными числами.

Project scope поддерживает text, number, date, single_select и iteration. Для select/iteration передаются названия существующих вариантов/итераций, контроллер разрешает ID. Native issue scope поддерживает text, number, date и single_select; POST принимает название select-варианта. Даты проверяет GitHub. Для Issue Type, labels, assignees, multi-select и других типов этот контроллер не предназначен: ошибка будет явной. Нативные Issue Fields не поддерживаются у PR. Подключённое к проекту нативное поле нужно указать в `issue`, а не в `project`: одинаковое имя scope не меняет.

Контроллер читает метаданные и текущие значения через авторизованный Octokit; пагинацию выполняет Octokit. До записи разрешаются обе секции и проверяются имена, варианты и типы. Неизвестные и неоднозначные имена — ошибка, `force` её не отключает. Проверка пустоты и последующая запись не атомарны: параллельная ручная правка может произойти между ними.

Каждый scope записывается одним запросом: Project REST PATCH `fields`, затем native REST POST `issue_field_values`. Пустой native POST не отправляется, PUT с заменой всех полей не используется. Общей транзакции нет. `FieldUpdateError.report.applied` содержит подтверждённые записи; `uncertain` — поля запроса с неизвестным результатом при ошибке API. Перед повтором такого запроса нужно прочитать состояние. Item после ошибки постхука остаётся в проекте; ошибка не маскируется успешным добавлением.

Для project scope нужны существующие права на запись Projects, для native scope — запись issues и доступ к Issue Fields организации. Автоматического расширения прав нет. Workflow устанавливает только runtime YAML-парсер, только когда input непустой; библиотека YAML загружается лениво. Настройки и права потребителя остаются его конфигурацией.

## Интеграционная проверка

`test-field-posthook.yml` использует штатный GitHub App и существующий sandbox из основных integration workflow. Проверяет записи обоих API, force/повтор, неизвестные поля/варианты, частичный результат и оба пути добавления PR. Использует реальные HTTP-запросы без моков. Для безопасного импортера App fixture PR заменяет настроенного bot-пользователя — как в существующем integration сценарии; отдельный настоящий Dependabot PR не создаётся. Закрытые PR исключаются будущей датой cutoff, проверяется только новейший открытый fixture PR. Созданные сущности закрываются; items и ветки сохраняются. JSON результата остаётся artifact прогона.
